PARTE 1 — VISÃO GERAL E IDENTIDADE DO JOGO
======================================================================

1.1. CONCEITO

WORLD ZERO é um jogo multiplayer de sobrevivência 2D com câmera
top-down, inspirado em elementos de jogos de sobrevivência como Project
Zomboid e Rust, mas com mapa, identidade visual, sistemas, nomes,
personagens, interface, conteúdo e código originais.

O jogador entra em um mundo hostil, coleta recursos, procura comida e
água, fabrica ferramentas, constrói uma base, enfrenta zumbis, animais e
outros jogadores, explora regiões perigosas e tenta sobreviver durante
uma temporada de sete dias reais.

O mundo continua existindo quando um jogador fecha o jogo. Outros
jogadores podem continuar explorando, construindo, atacando e alterando
o mundo.

1.2. CONFIGURAÇÃO DEFINIDA PELO USUÁRIO

-   Câmera: 2D top-down, vista de cima.
-   Mapa: gigante, dividido em regiões e carregado por partes.
-   Inimigos: zumbis e animais; NPCs sobreviventes podem ser adicionados
    em fase posterior, sem bloquear o primeiro lançamento.
-   PvP: sempre permitido, respeitando regras técnicas contra trapaças.
-   Capacidade-alvo: até 50 jogadores simultâneos por servidor/mundo.
-   Ciclo: servidor dura sete dias corridos, 24 horas por dia.
-   Final do ciclo: wipe completo do progresso do mundo e início de novo
    ciclo.
-   Plataformas: Android APK e versão web de teste.
-   Desenvolvimento: código versionado no GitHub e colaboração com IAs.
-   GitHub Pages: hospedagem da versão web estática, documentação e
    página de apresentação; não é o servidor multiplayer persistente.

1.3. PILARES DO JOGO

A. Sobrevivência: Fome, sede, saúde, ferimentos, temperatura/condições
ambientais em fase posterior, inventário limitado e necessidade de
abrigo.

B. Mundo persistente: O mundo não pausa quando o jogador sai. Alterações
importantes são salvas no servidor e recuperadas após reinicializações.

C. Risco e recompensa: Áreas com recursos raros atraem jogadores e
aumentam o risco de confronto.

D. Construção: Jogadores coletam materiais e montam abrigos, depósitos,
barricadas, portas, paredes e estruturas defensivas.

E. PvP: O combate entre jogadores é parte permanente do mundo. O
servidor valida movimento, dano, inventário, coleta e construção.

F. Temporadas de sete dias: Cada temporada cria uma disputa com começo,
meio e fim. O wipe reinicia o mundo e impede que bases antigas dominem
temporadas futuras.

1.4. ESCOPO DO PRIMEIRO JOGO COMPLETO

O primeiro lançamento jogável deve conter: - tela inicial e
criação/identificação de jogador; - lista de servidores e entrada em
servidor; - mundo 2D com câmera seguindo o jogador; - movimentação por
teclado e toque; - mapa dividido em chunks; - coleta de recursos; -
inventário e equipamentos básicos; - fome, sede e vida; - ciclo de dia e
noite; - zumbis básicos; - animais básicos; - combate corpo a corpo e
pelo menos uma arma de distância simples; - crafting básico; -
construção de base; - PvP validado pelo servidor; - morte e
reaparecimento; - salvamento persistente; - limite de 50 jogadores por
mundo; - temporada de sete dias e wipe automático; - interface mobile; -
build Android instalável; - documentação e testes.

Não tentar incluir no primeiro lançamento: - veículos complexos; -
barcos e aviões; - centenas de armas; - sistema de clãs avançado; - NPCs
humanos com IA complexa; - voz por proximidade; - mapa infinito sem
limites; - loja com dinheiro real; - sistema de modificação livre pelo
jogador. Esses itens ficam para atualizações futuras.

PARTE 2 — ARQUITETURA TÉCNICA
======================================================================

2.1. PRINCÍPIO DE ARQUITETURA

Separar o projeto em quatro partes:

1.  CLIENTE DO JOGO: Executa gráficos, áudio, interface, controles,
    animações e apresentação. Não decide sozinho resultados importantes
    do jogo.

2.  SERVIDOR AUTORITATIVO: É a autoridade sobre posição válida, combate,
    vida, inventário, coleta, construção, inimigos, relógio do mundo e
    regras da temporada.

3.  BANCO DE DADOS: Armazena contas, personagens, estado persistente do
    mundo, construções, inventários, eventos e dados das temporadas.

4.  HOSPEDAGEM E DISTRIBUIÇÃO: GitHub guarda o código e automatiza
    builds. GitHub Pages publica a versão web estática. Um serviço
    separado hospeda o servidor multiplayer e o banco.

2.2. TECNOLOGIAS RECOMENDADAS

Cliente: - TypeScript. - Phaser 3 para renderização e lógica visual
2D. - Vite para desenvolvimento e build web. - HTML/CSS para telas e
interface. - Capacitor para empacotar a aplicação web como APK Android.

Servidor: - Node.js em versão LTS suportada pelo projeto. -
TypeScript. - Colyseus para salas, conexão e sincronização
multiplayer. - Regras de jogo executadas no servidor. - WebSocket para
comunicação em tempo real.

Persistência: - PostgreSQL para dados permanentes. - Redis opcional para
cache, presença, filas e coordenação, se necessário. - Sistema de
snapshots e salvamento periódico. - Armazenamento de backups separado do
processo do jogo.

Ferramentas: - Git e GitHub. - GitHub Actions para testes e builds. -
Playwright ou ferramenta equivalente para testes de interface web. -
Testes unitários para regras de jogo. - Android Studio/SDK para gerar e
validar APK. - Docker para ambiente reproduzível, quando a hospedagem
escolhida permitir.

A versão exata de cada dependência deve ser escolhida e fixada no
package.json e no lockfile. Claude deve verificar compatibilidade atual
antes de instalar. Não usar versões aleatórias nem atualizar todas as
dependências sem necessidade.

2.3. VISÃO DA COMUNICAÇÃO

Fluxo simplificado:

JOGADOR ANDROID/WEB | | HTTPS: login, lista de servidores, dados de
conta | WSS: movimento, ações e eventos multiplayer v API / GATEWAY DE
AUTENTICAÇÃO | v SERVIDOR DE JOGO — SALA DO MUNDO | +—- valida movimento
e velocidade +—- valida combate e dano +—- valida coleta e crafting +—-
valida construção e permissões +—- atualiza zumbis e animais +—- salva
eventos e snapshots | +——————–> POSTGRESQL | +——————–> REDIS (opcional)

O cliente envia intenções, não resultados finais. Exemplo: o cliente
envia “quero atacar o alvo X”; o servidor verifica distância, arma
equipada, tempo de ataque, linha de visão, estado do jogador e alvo.
Somente o servidor calcula e confirma o dano.

2.5. MONOREPO

Preferir um monorepo para compartilhar tipos e regras seguras entre
cliente e servidor. Usar pnpm workspaces ou outra solução consistente.

O pacote shared pode conter: - tipos de mensagens; - identificadores de
itens; - definições de atributos; - schemas de validação; - constantes
públicas; - versões do protocolo.

O cliente nunca deve receber segredos nem lógica que permita manipular o
servidor. Regras críticas devem existir e ser executadas no servidor.

PARTE 3 — MUNDO GIGANTE E GERAÇÃO DO MAPA
======================================================================

3.1. MAPA POR CHUNKS

Não carregar o mapa inteiro na memória do celular. Dividir o mundo em
chunks. Um chunk é uma região quadrada de tiles. Começar testando chunks
de 32x32 ou 64x64 tiles; escolher o tamanho após medir memória,
desempenho e tráfego.

O servidor mantém os dados relevantes dos chunks próximos dos jogadores.
O cliente recebe os chunks visíveis e uma margem para evitar
carregamento perceptível.

Cada chunk deve ter: - coordenada X/Y; - identificador do
mundo/temporada; - terreno; - objetos estáticos; - recursos
coletáveis; - estruturas construídas; - entidades vivas relevantes; -
versão e data do último salvamento.

3.2. TAMANHO E LIMITES

“Mapa gigante” não significa mundo infinito. Para a primeira versão,
criar um mundo grande com limites claros e expansão possível. O tamanho
final deve ser definido por testes de desempenho, armazenamento e custo
de hospedagem.

Começar com um mapa de teste menor. Validar streaming de chunks e só
então aumentar a dimensão. Não gerar milhares de chunks sem medir
impacto.

3.3. REGIÕES

O mapa deve conter regiões com identidade e recursos próprios:

-   Cidade: casas, prédios, lojas, mercados, farmácias e hospitais.
-   Floresta: madeira, animais, pedras e locais de acampamento.
-   Zona rural: fazendas, celeiros, plantações e poços.
-   Zona industrial: metal, ferramentas, componentes e combustível.
-   Área militar: recursos raros e alto risco.
-   Estradas: conectam regiões e criam pontos de emboscada.
-   Áreas contaminadas/perigosas: conteúdo futuro, com risco e
    recompensa.

3.4. GERAÇÃO PROCEDURAL

Usar uma seed por temporada. A mesma seed deve produzir o mesmo
mapa-base. A seed permite reproduzir bugs e validar o mundo.

A geração deve seguir etapas: 1. criar terreno e biomas; 2. definir
água, rios, lagos e obstáculos; 3. criar estradas e conexões; 4.
posicionar cidades e pontos de interesse; 5. distribuir edifícios; 6.
posicionar recursos; 7. definir pontos de surgimento de inimigos; 8.
validar que as áreas são alcançáveis; 9. salvar metadados da geração.

O conteúdo procedural deve ser determinístico. Construções e alterações
dos jogadores são salvas separadamente do mapa-base.

3.5. NAVEGAÇÃO

O jogador precisa de: - minimapa; - mapa completo; - posição atual; -
marcadores próprios; - nomes de regiões; - ícones de locais
importantes; - opção de ocultar o mapa para economizar desempenho.

Não mostrar automaticamente a posição de outros jogadores no mapa
global. Isso preserva exploração e evita facilitar rastreamento.

3.6. DESTRUIÇÃO E ALTERAÇÃO DO MUNDO

Na primeira versão: - recursos coletáveis podem desaparecer e reaparecer
conforme regras; - portas e janelas podem ter estados; - objetos simples
podem ser destruídos; - estruturas construídas são persistidas; -
alterações grandes de terreno ficam para fase futura.

======================================================================
PARTE 4 — PERSONAGEM E SOBREVIVÊNCIA
======================================================================

4.1. ATRIBUTOS

Cada personagem possui: - vida; - fome; - sede; - energia/fadiga; -
inventário; - equipamento; - estado de ferimento; - posição; - estado de
conexão; - identificador persistente.

Começar com vida, fome, sede e energia. Não implementar dezenas de
atributos antes de testar o ciclo básico.

4.2. FOME E SEDE

Fome e sede diminuem com o tempo do mundo. Corrida, combate e atividades
podem aumentar o consumo. Comer e beber recuperam os medidores conforme
o item.

Quando fome ou sede chegam a níveis críticos: - aplicar penalidades
graduais; - reduzir recuperação; - causar dano somente após aviso e
período de tolerância configurável.

O balanceamento deve ser testado para não obrigar o jogador a ficar
conectado sem parar. O objetivo é sobrevivência, não punição abusiva por
desconectar.

4.3. VIDA E FERIMENTOS

Implementar: - dano de zumbis; - dano de animais; - dano de outros
jogadores; - dano ambiental simples; - cura com itens; - morte; -
reaparecimento.

Fases futuras podem adicionar sangramento, fraturas, infecções e
tratamento avançado. O sistema inicial precisa ser claro e testável.

4.4. INVENTÁRIO

Inventário em grade ou slots, adequado a telas pequenas. Cada item
tem: - ID único de definição; - nome; - categoria; - peso; - quantidade
máxima por pilha; - durabilidade, se aplicável; - propriedades; -
ícone; - raridade apenas se fizer sentido.

O servidor valida toda movimentação de item. Nunca confiar no valor de
quantidade ou peso enviado pelo cliente.

4.5. EQUIPAMENTOS

Slots iniciais: - mão principal; - mão secundária, se a regra
permitir; - roupa; - mochila.

Equipamentos podem alterar capacidade, proteção ou velocidade, com
limites claros para evitar desequilíbrio.

4.6. CICLO DE DIA E NOITE

O tempo é controlado pelo servidor. Todos os clientes recebem a mesma
hora do mundo. A duração de um dia do jogo deve ser configurável. A
primeira versão pode usar um ciclo curto para teste e um ciclo mais
longo no servidor público.

Noite: - visibilidade reduzida; - iluminação por fontes; - maior tensão
de exploração; - regras de spawn ajustáveis por região e horário.

Não fazer o relógio depender do horário do celular.

======================================================================
PARTE 5 — ITENS, COLETA, CRAFTING E CONSTRUÇÃO
======================================================================

5.1. RECURSOS INICIAIS

-   madeira;
-   pedra;
-   fibra;
-   sucata metálica;
-   tecido;
-   comida;
-   água;
-   remédios básicos;
-   munição;
-   combustível, em fase posterior.

5.2. COLETA

O jogador se aproxima de um recurso e solicita coleta. O servidor
verifica: - distância; - ferramenta necessária; - quantidade
disponível; - tempo de ação; - inventário livre; - se outro jogador já
coletou o recurso.

O servidor responde com sucesso ou motivo da recusa.

5.3. CRAFTING

Cada receita define: - ingredientes; - quantidades; - tempo; -
ferramenta necessária; - resultado; - estação de trabalho, se houver.

Receitas iniciais: - machado improvisado; - picareta simples; - lança; -
tocha; - bandagem; - fogueira; - parede de madeira; - porta; - baú; -
bancada simples.

O servidor confere os ingredientes e realiza a transação de forma
atômica: ou consome tudo e entrega o resultado, ou não altera o
inventário.

5.4. CONSTRUÇÃO

Peças iniciais: - fundação; - parede; - porta; - janela/barricada; -
baú; - fogueira; - bancada; - telhado simples, se suportado pelo sistema
de construção escolhido.

Regras: - validar posição e colisão; - impedir construção em áreas
bloqueadas; - validar materiais; - validar distância do jogador; -
impedir sobreposição inválida; - salvar no banco; - permitir dano e
destruição conforme balanceamento; - impedir que uma mensagem repetida
duplique construções.

5.5. BASES E INVASÕES

Como PvP é sempre permitido, bases podem ser invadidas. A primeira
versão deve ter defesa simples e regras transparentes.

Não implementar proteção invulnerável que contradiga PvP permanente.
Pode existir custo/tempo de destruição para impedir ataques
instantâneos.

5.6. BAÚS E ARMAZENAMENTO

Conteúdo de baús é persistente até o wipe. O servidor valida abertura,
distância, permissão e transferência de itens. Evitar duplicação por
requisições repetidas.

======================================================================
PARTE 6 — ZUMBIS, ANIMAIS E COMBATE
======================================================================

6.1. ZUMBIS

Comportamentos iniciais: - ficar parado ou vagar; - detectar jogador por
distância; - perseguir; - atacar quando próximo; - perder interesse após
distância/tempo; - retornar a uma área de referência ou vagar
novamente; - morrer e gerar loot configurado.

A IA dos zumbis deve rodar no servidor. Não atualizar cada zumbi em
frequência máxima se não houver jogador por perto. Usar simulação por
proximidade e atualização em intervalos controlados.

6.2. ANIMAIS

Começar com poucos tipos: - animal passivo que foge; - animal que pode
atacar quando provocado; - animal que fornece recurso quando derrotado,
se apropriado ao design.

A primeira versão pode ter apenas dois comportamentos simples. Não criar
ecossistema complexo antes de medir o servidor.

6.3. COMBATE

Tipos iniciais: - ataque corpo a corpo; - ataque à distância simples; -
dano de zumbi; - dano de animal; - PvP.

O servidor valida: - distância; - direção/alcance; - cooldown; - arma; -
munição; - linha de visão quando aplicável; - estado do atacante e do
alvo; - velocidade de ataque permitida.

O cliente pode prever animações para resposta visual, mas o resultado
final é sempre confirmado pelo servidor. Se a previsão estiver errada,
corrigir estado.

6.4. ARMAS E FERRAMENTAS INICIAIS

Começar pequeno: - ferramenta improvisada; - machado; - lança; - arma de
fogo simples em fase seguinte; - munição limitada.

Cada arma precisa de dano, alcance, velocidade, durabilidade, ruído e
animação. Não adicionar grande catálogo sem balancear.

6.5. MORTE E REAPARECIMENTO

Regras iniciais sugeridas: - ao morrer, o personagem deixa uma
mochila/caixa de loot no local; - outros jogadores podem pegar o
conteúdo; - o jogador reaparece em um ponto válido; - equipamento e
inventário perdidos seguem a regra da temporada; - o servidor impede
duplicação de itens durante morte, desconexão e reconexão.

O usuário deve poder entender claramente o que perde antes de entrar no
servidor.

======================================================================
PARTE 7 — MULTIPLAYER, SERVIDORES E TEMPORADAS DE 7 DIAS
======================================================================

7.1. CAPACIDADE

Cada mundo tem limite de 50 jogadores simultâneos. A capacidade real
deve ser validada com teste de carga. Não anunciar 50 jogadores em
produção antes de simular 50 clientes ou bots e medir CPU, memória,
latência e estabilidade.

7.2. SERVIDORES

Cada servidor é um mundo independente, com: - ID; - nome; - região de
hospedagem; - população atual; - limite de 50; - ping aproximado; -
status; - horário de início da temporada; - horário previsto para
wipe; - seed do mapa; - versão do jogo.

A lista de servidores mostra: - nome; - jogadores online/50; - tempo
restante da temporada; - status; - ping, quando conhecido; - regras
principais.

7.3. MUNDO PERSISTENTE

O mundo continua rodando mesmo quando um jogador sai. Isso exige
processo de servidor ativo e armazenamento persistente.

O servidor deve salvar: - posição e estado dos jogadores; -
inventário; - construções; - baús; - recursos alterados; - estado
importante de NPCs/inimigos; - relógio do mundo; - eventos de temporada.

Não é necessário salvar cada movimento em banco a cada frame. Usar
memória para simulação e persistência periódica/event-driven, com
estratégia contra perda de dados em falhas.

7.4. TEMPORADA DE SETE DIAS

O relógio da temporada é definido pelo servidor, usando UTC como
referência interna para consistência. A interface pode mostrar o horário
local do jogador.

Cada temporada: 1. cria um novo ID; 2. define seed; 3. gera o mapa; 4.
inicia o relógio; 5. aceita jogadores até o limite; 6. registra
estatísticas; 7. encerra ao completar sete dias corridos; 8. bloqueia
novas ações no mundo encerrado; 9. grava resultado final; 10.
remove/resetta dados de gameplay daquele mundo; 11. gera a nova
temporada e novo mapa.

O wipe remove: - personagens e progresso daquele mundo; - inventários; -
bases e construções; - baús; - recursos alterados; - estados de
entidades; - dados temporários da temporada.

Preservar somente dados de conta necessários para login e histórico
agregado de temporadas, se aprovado: ID de conta, nome público,
estatísticas históricas e resultados. Nenhum item ou vantagem de
gameplay deve atravessar o wipe.

7.5. SEGURANÇA DO WIPE

Não apagar dados diretamente sem proteção. - usar status de temporada:
ACTIVE, CLOSING, ARCHIVED, RESETTING, ACTIVE; - impedir novas ações
durante fechamento; - criar snapshot/arquivo de estatísticas; - executar
reset por transação ou procedimento idempotente; - registrar logs; -
verificar integridade; - iniciar novo mundo somente após validação; -
permitir recuperação de falha sem duplicar temporadas.

O reset deve ser automático no backend, não depender de alguém abrir o
jogo.

7.6. DESCONEXÃO

Ao desconectar: - marcar jogador offline; - persistir estado
necessário; - remover presença após timeout; - decidir se o personagem
permanece no mundo ou desaparece.

Regra recomendada para primeira versão: personagem fica no mundo por um
curto período configurável para evitar abuso de desconexão durante
combate; depois fica offline e não pode ser controlado. Definir
claramente o comportamento antes do lançamento.

7.7. RECONEXÃO

O jogador deve voltar ao mesmo servidor e recuperar estado salvo. Se o
servidor cair, deve ser possível recuperar o último snapshot válido e os
eventos persistidos desde então, dentro da política de tolerância a
falhas.

7.8. MATCHMAKING

Primeira versão: - lista de servidores; - botão entrar; - recusar se
lotado; - reconectar ao servidor anterior quando possível.

Futuro: - filtro por região; - favoritos; - convite por código; -
servidor privado; - matchmaking por ping.

PARTE 8 — PROTOCOLO DE REDE E SEGURANÇA
======================================================================

8.1. MENSAGENS

Definir mensagens tipadas e versionadas. Exemplos conceituais:

CLIENTE -> SERVIDOR: - PLAYER_INPUT - REQUEST_INTERACT -
REQUEST_ATTACK - REQUEST_PICKUP - REQUEST_CRAFT - REQUEST_BUILD -
REQUEST_INVENTORY_MOVE - REQUEST_USE_ITEM - REQUEST_RESPAWN

SERVIDOR -> CLIENTE: - WORLD_SNAPSHOT - PLAYER_STATE - ENTITY_UPDATE -
INVENTORY_UPDATE - COMBAT_EVENT - CHAT_EVENT, se chat for incluído -
SERVER_NOTICE - SEASON_UPDATE - ACTION_REJECTED

Claude deve definir schemas concretos com validação, tamanho máximo e
versão. Não aceitar objetos arbitrários ou dados ilimitados enviados
pelo cliente.

8.2. AUTORIDADE

O servidor é autoridade sobre: - posição final; - velocidade; - colisões
importantes; - vida; - dano; - inventário; - loot; - crafting; -
construção; - tempo; - spawn; - temporada.

8.3. ANTI-CHEAT BÁSICO

Implementar: - validação de velocidade; - validação de alcance; -
cooldowns; - limite de mensagens; - validação de inventário; - validação
de posição; - proteção contra duplicação; - IDs de ação idempotentes; -
logs de ações suspeitas; - limite de tamanho de payload; - autenticação
e autorização.

Não confiar em valores de dano, velocidade, quantidade, cooldown ou
posição calculados exclusivamente pelo cliente.

8.4. AUTENTICAÇÃO

Começar com login simples e seguro, com opção de conta de teste durante
desenvolvimento. Tokens de sessão devem ter validade e ser armazenados
de forma segura. Nunca colocar segredo administrativo ou credencial de
banco no APK.

8.5. PRIVACIDADE

Coletar somente dados necessários. Não expor e-mail ou identificadores
privados na lista de jogadores. Definir política de privacidade antes de
distribuição pública.

PARTE 12 — HOSPEDAGEM, GITHUB E APK
======================================================================

12.1. PAPEL DO GITHUB

GitHub será usado para: - armazenar código; - histórico de alterações; -
issues e tarefas; - documentação; - revisão de mudanças; - GitHub
Actions; - geração automatizada de builds.

12.2. PAPEL DO GITHUB PAGES

GitHub Pages pode hospedar: - página de apresentação; - versão web
estática do cliente; - arquivos públicos do frontend; - documentação.

GitHub Pages NÃO hospeda: - processo Node.js contínuo; - servidor
Colyseus; - banco PostgreSQL; - mundo multiplayer rodando 24/7; -
tarefas de wipe que precisam executar sem usuário conectado.

Não tentar usar Pages como servidor de jogo.

12.3. BACKEND

Escolher hospedagem que suporte: - processo Node.js persistente; -
WebSocket; - conexões simultâneas; - armazenamento persistente; -
variáveis de ambiente; - backups; - monitoramento.

Serviços gratuitos podem dormir, limitar uso ou encerrar processos.
Fazer uma tabela de opções atualizada na época do deploy e verificar: -
horas gratuitas; - política de suspensão; - memória e CPU; - limite de
conexões; - tráfego; - armazenamento; - região; - suporte a WebSocket; -
persistência de disco; - custo quando o limite for excedido.

Se nenhuma opção gratuita garantir 24/7, informar isso claramente.
Desenvolver localmente e testar com plano gratuito é possível, mas o
servidor público persistente pode exigir hospedagem paga ou servidor
próprio.

12.4. APK

Fluxo esperado: 1. construir cliente web; 2. validar build; 3.
sincronizar com Capacitor; 4. abrir projeto Android; 5. configurar
identificador do aplicativo; 6. gerar APK debug para testes; 7. instalar
em aparelho real; 8. testar conexão e controles; 9. gerar APK release
assinado quando aprovado.

A chave de assinatura release deve ficar fora do Git e protegida. Nunca
comprometer keystore ou senha no repositório.

12.5. CI/CD

GitHub Actions deve: - instalar dependências pelo lockfile; - executar
lint; - executar testes; - construir cliente web; - verificar tipos; -
opcionalmente gerar artefato APK debug; - publicar Pages somente após
aprovação/configuração.

Não publicar automaticamente uma versão instável no servidor público.

PARTE 13 — TESTES E CRITÉRIOS DE ACEITAÇÃO

13.1. TESTES UNITÁRIOS

13.5. CRITÉRIOS PARA DECLARAR O MVP PRONTO

O MVP só pode ser chamado de pronto quando: - o jogador consegue iniciar
e entrar em um servidor; - dois ou mais jogadores se veem e se

sair e voltar; - servidor recupera estado após reinício; - relógio de
temporada é consistente; - wipe de sete dias foi testado em ambiente de
teste; - cliente Android instala e joga; - testes básicos passam; -
limitações conhecidas estão documentadas.

PARTE 15 — REGRAS DE QUALIDADE E DECISÕES
======================================================================

-   Não criar um servidor multiplayer falso que apenas simula jogadores
    localmente.

-   Não adicionar serviço pago sem explicar custo e pedir aprovação.

-   Não colocar tokens em arquivos versionados.
-   Não adicionar assets sem verificar licença.
-   Não apagar arquivos existentes sem aprovação.
-   Não misturar lógica visual com regras autoritativas do servidor.
-   Manter o projeto executável ao final de cada etapa.
-   Atualizar documentação e changelog.
-   Preferir soluções simples que possam ser mantidas por uma equipe
    pequena.

RESUMO FINAL
======================================================================

WORLD ZERO será um jogo 2D top-down de sobrevivência multiplayer, com
mapa gigante dividido em chunks, zumbis, animais, PvP sempre ativo,
construção, coleta, crafting, inventário e servidores persistentes de
até 50 jogadores.

Cada servidor terá temporadas de sete dias corridos, com wipe completo
do progresso de gameplay ao final. Contas e histórico agregado podem
permanecer, mas nenhum item, base ou vantagem de jogo passa para a
próxima temporada.

O cliente será feito com Phaser 3 e TypeScript, empacotado para Android
com Capacitor. O multiplayer será executado em backend Node.js/Colyseus,
com PostgreSQL para persistência. GitHub Pages hospedará somente a
versão estática web e a página do projeto. O backend precisa de
hospedagem própria compatível com processos persistentes e WebSocket.

A implementação será feita em 18 etapas, começando pela auditoria do
repositório e terminando com teste de carga, APK e publicação. Claude
executa uma etapa por vez, com testes e aprovação entre etapas.
